# T-1.4  A library change mid-commit must not resurrect stale engine state

file: Swiper/ViewModels/AppModel.swift, SwiperKitTests/
spec: SPEC 6.7
blocked_by: T-1.2
status: in-progress
done_when: a test proves a change arriving during confirmDeletion() cannot overwrite the post-commit state

## Verbatim SPEC clause
> 6.7  After the commit, only assets that are confirmed gone count as deleted.

## The hazard
`library.changeHandler` fires on EVERY PhotoKit change — including the changes Swiper
itself causes during a favorite or a deletion commit. It calls `reloadLibrary()`, which
rebuilds `engine` from persistence. Meanwhile `confirmDeletion()` holds a local copy of
the engine taken before the await, and writes it back afterwards. The stale write can
overwrite newer state.

## Required change
Make the commit path not clobber newer state. Simplest correct option: after the awaits
in `confirmDeletion()`, re-read the current engine instead of writing back the local
copy taken before the await. If that is not sufficient, guard the reload with a flag that
is set for the duration of the commit.

Add a test that drives the sequence: start a commit, deliver a library change during the
await, and assert the final engine reflects the commit and not the stale snapshot. Use
`FakePhotoLibrary` + `InMemorySessionStore` — never a real library.

## Do not
restructure `AppModel` here (that is T-4.1), change the engine, or touch `PhotoKitLibrary`.

## Report
The test's real output, the sequence it drives, `git diff --stat`.
